DEVELOPMENT in Oracle using AI Lab - מסמך תכולה ותוכנית עבודה

מטרה: להקים מעבדת פיתוח Oracle מבודדת שבה Codex/AI מפתח אובייקטי Oracle לפי אפיון, מבצע בדיקות וסקירת קוד, ולבסוף אורז תוצר שניתן להעביר תאורטית לסביבת פיתוח/בדיקות ארגונית.

סוג מסמך: מסמך תכולה, עקרונות מחייבים ותוכנית עבודה למעבדה. זה אינו אפיון עסקי של use case ספציפי.

גרסה: 0.2

תאריך: 2026-05-19

1. שמות הפרויקט ומשאבי runtime

Decision 001: שם התצוגה של הפרויקט הוא DEVELOPMENT in Oracle using AI Lab.
Decision 002: שם ה-repository הטכני חייב להיות oracle-dev-ai-lab.

משאבי Docker של המעבדה חייבים להשתמש בשמות הבאים:

Repository: oracle-dev-ai-lab
Container:  oracle-dev-ai-lab-db
Volume:     oracle-dev-ai-lab-u01
Network:    oracle-dev-ai-lab-net
PDB:        FREEPDB1
כלל מחייב: שמות אלה מחייבים בכל scripts, מסמכי עבודה, בדיקות והנחיות Codex. אין להשתמש בשמות חלופיים ללא החלטת תכנון מפורשת.

2. עקרונות יסוד

Decision 003: GitHub הוא מקור האמת היחיד. בסיס הנתונים הוא תוצר התקנה זמני שניתן למחיקה ושחזור.
Decision 004: המעבדה תשתמש ב-container נפרד, ב-volume נפרד וברשת Docker נפרדת. אין להשתמש ב-Oracle container קיים.
Decision 005: המעבדה חייבת לרוץ על Oracle AI Database 26ai Free בתוך Docker.
Decision 006: Codex אינו רשאי להריץ DDL או DML אד-הוק ישירות מול בסיס הנתונים. כל שינוי DB חייב להופיע בקובץ SQL מנוהל Git ולהיות מורץ דרך scripts רשמיים בלבד.
Decision 007: בשלב הראשון המעבדה מיועדת לאובייקטי Oracle בלבד: tables, constraints, indexes, views, packages, package bodies, triggers רק אם יש הצדקה, seed data, tests, review ו-packaging. REST, ORDS, APEX ו-UI אינם חלק מהשלב הראשון.
כלל הזהב: No database change is valid unless it exists as a versioned SQL file and can be installed on a clean lab database by the official scripts.

3. מדיניות גרסת Oracle ותאימות

המעבדה חייבת להשתמש ב-Oracle AI Database 26ai Free בתוך Docker.

למרות שבסביבות הארגוניות נעשה כיום שימוש עיקרי ב-Oracle 19c, המעבדה מכוונת במכוון לגרסה עדכנית יותר לצורכי פיתוח מבודד, למידה והתנסות קדימה.

כלל מחייב: ה-MVP אינו מבטיח תאימות ל-Oracle 19c. כל דרישת תאימות עתידית ל-Oracle 19c חייבת להיות ממומשת כשכבת בדיקות וסקירה נפרדת.

4. גבולות המעבדה

  • אין חיבור לסביבת Production.
  • אין חיבור ישיר לסביבת פיתוח/בדיקות ארגונית על ידי Codex.
  • אין חיבור לבסיסי נתונים ארגוניים, משותפים, פיתוח, בדיקות, staging או production.
  • אין סיסמאות או secrets בקוד.
  • Codex רשאי להריץ SELECT בלבד, ורק לצורכי diagnostics, metadata inspection, compile checks, test verification ו-review.
  • שינויי schema מותרים רק דרך קבצים מנוהלים ו-script התקנה רשמי.
  • כל תוצר חייב להיות ניתן להתקנה מחדש על בסיס נתונים נקי.
  • כל assumption מהותי חייב להירשם ב-task, בדוח review או במסמך החלטות. אין להמציא התנהגות שלא הוגדרה.

5. MVP ראשון - Infrastructure MVP

Decision 008: ה-MVP הראשון הוא Infrastructure MVP. הוא אינו מימוש פונקציונלי של מערכת עסקית.

ה-Infrastructure MVP חייב להוכיח שהמעבדה מסוגלת:

  • להקים ולאפס סביבת Oracle Docker מבודדת.
  • ליצור משתמשים וסכמות מעבדה.
  • להריץ install scripts מבוקרים.
  • להריץ בדיקות smoke ל-repository ול-DB.
  • להריץ review scripts.
  • לייצר release package.
כלל מחייב: ה-Infrastructure MVP אינו מחייב מימוש package עסקי אמיתי ב-PL/SQL ואינו מחייב feature פונקציונלי מלא.

פיתוח פונקציונלי של use case ניהול ההעברות לייצור יתחיל רק לאחר שה-Infrastructure MVP יציב, ניתן לשחזור ועובר בדיקות.

Smoke Object מינימלי

כדי להוכיח install, test, review ו-packaging מקצה לקצה, ה-Infrastructure MVP יכלול אובייקט smoke מינימלי בלבד.

Suggested smoke object:
LAB_SMOKE_TEST
כלל מחייב: אובייקט smoke אינו feature עסקי. הוא קיים רק כדי להוכיח שה-pipeline התשתיתי עובד.

9. Specification-to-Tasks Pipeline

האפיון ייכתב כמסמך HTML מובנה. ממנו ייגזרו תוצרים מכונתיים ותפעוליים:

spec.html
  -> spec.json
  -> TODO.md
  -> tasks/Txxx-*.md
  -> db/generated/*
  -> db/src/*
  -> review report
  -> release package

כלל עקיבות

כל TODO, task, קובץ SQL, בדיקה והערת review חייבים להצביע ל-requirement id, task id או infrastructure decision מפורש.

10. פורמט spec.html

מסמך האפיון צריך להיות HTML סמנטי, עם sections ו-requirement ids קבועים.

<article id="spec" data-spec-id="001" data-version="0.1.0">
  <section id="business-goal" data-required="true">...</section>
  <section id="scope" data-required="true">...</section>
  <section id="out-of-scope" data-required="true">...</section>
  <section id="entities" data-required="true">...</section>
  <section id="plsql-api" data-required="false">...</section>
  <section id="acceptance-criteria" data-required="true">...</section>
</article>
כלל מחייב: section של PL/SQL API אינו חובה ב-Infrastructure MVP. הוא יהפוך לרלוונטי רק באיטרציות פונקציונליות.

11. פורמט משימת Codex

# Txxx - Task title

## Task
תיאור קצר וממוקד של המשימה.

## Source requirements
- REQ-...
- AC-...
- DEC-...

## Files to create or update
- db/src/...
- scripts/...
- tools/...

## Required behavior
מה בדיוק צריך להיווצר או להשתנות.

## Success criteria
1. הקובץ נוצר או עודכן.
2. ההתקנה עוברת על DB נקי, אם המשימה נוגעת ל-DB.
3. אין invalid objects, אם המשימה יוצרת אובייקטי DB.
4. scripts/test.sh quick עובר.
5. אין שינוי בקבצים לא קשורים.

## Testing
Run:

scripts/test.sh quick

If debugging is needed:

scripts/test.sh full

## Mandatory Constraints
- Codex MUST work only inside this repository.
- Codex MUST connect only to the local Docker container named oracle-dev-ai-lab-db.
- Codex MUST NOT connect to organizational databases.
- Codex MUST NOT execute ad-hoc DDL or DML.
- Codex MAY execute SELECT statements only for diagnostics, metadata inspection, compile checks, tests, and review.
- Every schema change MUST be represented as a versioned SQL file.
- Every change MUST be traceable to a requirement id, task id, or explicit infrastructure decision.
- Codex MUST NOT modify unrelated files.
- Codex MUST stop and report if a required assumption is missing.

13. בדיקות

בדיקות Repo

  • מבנה תיקיות תקין.
  • כל task כולל success criteria.
  • כל task כולל source requirements או decision id.

  • אין invalid objects.
  • משתמשי המעבדה קיימים.
  • grants מוגבלים.
  • אין אובייקטים ב-SYSTEM/SYSAUX.
  • אובייקט smoke מינימלי נוצר ונבדק.
  • כל אובייקט DB שנוצר קיים גם כקובץ versioned ב-repository.
